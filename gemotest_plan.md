# Gemotest Content Pipeline — План разработки

## Цель

Система для автоматической генерации и верификации медицинского контента для страниц анализов лаборатории Гемотест.

**Вход:** Название анализа (напр., "ТТГ") или маркетинговый комплекс (напр., "Щитовидная железа: ТТГ + Т4св + АТ-ТПО").

**Выход:** Полный черновой вариант описания анализа — все нужные блоки заполнены, ключевые факты верифицированы через веб-поиск, источники указаны, неверифицированные данные помечены флагом.

**Аналог:** sf_pipeline (описан ниже в Приложении) — делает то же самое для бизнес-историй. Архитектура и паттерны берутся оттуда.

## Деплой и инфраструктура

### Схема

```
GitHub Repository (gemotest_pipeline)
│
├── .github/workflows/run.yml    ← GitHub Actions: запуск по кнопке
├── pipeline/                    ← Python код
├── docs/                        ← GitHub Pages (статика)
│   ├── index.html               ← UI для просмотра результатов
│   └── results/
│       ├── ttg.json             ← Результат для ТТГ
│       └── vitamin_d.json       ← Результат для Витамина D
└── .env.example
```

### Как работает GitHub Actions + Pages

1. Пользователь открывает страницу на GitHub Pages
2. Нажимает "Run" → вводит название анализа
3. Через GitHub API запускается `workflow_dispatch`
4. Actions запускает `pipeline/pipeline.py "ТТГ"`
5. Результат (JSON) коммитится в `docs/results/`
6. GitHub Pages автоматически обновляется
7. Пользователь видит результат на той же странице

### Альтернатива — локальный запуск

Для разработки и тестирования — локальный сервер, аналогичный sf_pipeline (FastAPI + SSE + monitor.html). Можно переключаться между режимами.

Блоки не финализированы — каждый блок прорабатывается отдельно: уточняются описание, инструкции для LLM, формат вывода. Это делается по ходу разработки.

## Пайплайн — детальный поток

### Фаза 1: LLM Knowledge Gathering (аналог sf_pipeline)

Один запрос к Gemini = один широкий проход + N тематических проходов.

**Структура промпта:**

```
Ты медицинский редактор лаборатории. Опиши всё что знаешь об анализе «ТТГ».
Используй формат — одна запись на блок:

BLOCK: [ID] · [название блока]
CONTENT:
[содержимое]
CONFIDENCE: [high / medium / low]
VERIFY: [ключевые факты для проверки через веб-поиск]

---

[Широкий первый проход — все что знаешь]

Когда закончишь, напиши точно:

=== ВТОРОЙ ПРОХОД ===

Теперь сосредоточься только на: Нормы и референсные значения
Опиши нормы для: взрослых (м/ж), детей по возрастам, беременных по триместрам, пожилых.
После каждого раздела спроси себя: «Есть ли ещё важный подраздел?» — если да, добавь.
Тот же формат.

=== ТРЕТИЙ ПРОХОД ===

Теперь сосредоточься только на: Показания и симптомы
...
```

**Проходы (draft, уточняются в процессе):**
- ВТОРОЙ: Нормы и референсные значения
- ТРЕТИЙ: Показания, симптомы, группы риска
- ЧЕТВЁРТЫЙ: Подготовка к исследованию, правила сдачи
- ПЯТЫЙ: Интерпретация результатов, путь пациента
- ШЕСТОЙ: Методология, аналитические характеристики
- СЕДЬМОЙ: Лекарственные взаимодействия, интерференции
- ВОСЬМОЙ: Связанные анализы, сравнение, алгоритмы
- ДЕВЯТЫЙ: FAQ, мифы, мета-контент

**Self-prompting** (как в sf_pipeline):  
`«Есть ли ещё важная информация по этому блоку?»` — после каждого раздела в тематическом проходе.

### Фаза 2: Web Verification (Serper + Tavily)

Для каждого блока с `VERIFY: [...]` — делаем проверку:

1. **Serper (Google Search)** → список URL по ключевым запросам
   - Клинические рекомендации МЗ РФ, ЕТА, ATA
   - Страницы конкурентов (Mayo Clinic, Labcorp, Helixbook.ru)
   - PubMed
2. **Tavily Extract** → скрейпинг HTML
3. **Gemini Flash Lite** → факт-карточка:
   ```
   ПОДТВЕРЖДАЕТ: [факты совпадающие с нашим текстом]
   ДОБАВЛЯЕТ: [новые данные, цифры, ссылки]
   ПРОТИВОРЕЧИТ: [расхождения]
   ИСТОЧНИК: [название документа / гайдлайна]
   ```
4. **Gemini Flash** → обновлённый блок с верифицированными фактами + ссылки

### Фаза 3: Сборка

Все блоки → единый документ-черновик.

**Формат финального блока:**
```markdown
## Нормы (Блок 3)
**Статус:** ✓ Верифицировано · 3 источника
**Источники:** [Приказ МЗ РФ №804н], [ATA Guidelines 2022], [helixbook.ru/tests/ttg]

| Группа | Норма | Единицы |
|--------|-------|---------|
| Взрослые 18–60 лет | 0,4 – 4,0 | мЕд/л |
| Беременные I триместр | 0,1 – 2,5 | мЕд/л |
| ...

⚠️ *Нормы могут отличаться в зависимости от метода и лаборатории. Интерпретацию проводит врач.*
```

## GitHub Actions Workflow

```yaml
# .github/workflows/run.yml
name: Run Gemotest Pipeline

on:
  workflow_dispatch:
    inputs:
      analysis_name:
        description: 'Анализ (напр. ТТГ)'
        required: true
        type: string
      complex_names:
        description: 'Доп. анализы в комплексе (через запятую)'
        required: false
        type: string
      blocks:
        description: 'ID блоков (пусто = все)'
        required: false
        type: string

jobs:
  pipeline:
    runs-on: ubuntu-latest
    permissions:
      contents: write  # для git push в docs/

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: 'pip'

      - run: pip install -r requirements.txt

      - name: Run pipeline
        env:
          GEMINI_API_KEY: ${{ secrets.GEMINI_API_KEY }}
          SERPER_API_KEY: ${{ secrets.SERPER_API_KEY }}
          TAVILY_API_KEY: ${{ secrets.TAVILY_API_KEY }}
        run: |
          python pipeline/pipeline.py \
            --analysis "${{ inputs.analysis_name }}" \
            --complex "${{ inputs.complex_names }}" \
            --blocks "${{ inputs.blocks }}"

      - name: Commit results
        run: |
          git config user.name "gemotest-bot"
          git config user.email "bot@gemotest"
          git add docs/results/
          git commit -m "Results: ${{ inputs.analysis_name }}" || echo "No changes"
          git push
```

## GitHub Pages UI (docs/index.html)

Статическая страница без сервера. При загрузке читает JSON из `docs/results/`.

**Главная (index.html):**
- Список доступных анализов (из `docs/results/*.json`)
- Для каждого: дата, статус (сколько блоков заполнено / верифицировано)

- Поле ввода анализа
- Кнопка "Запустить" → вызывает GitHub API → запускает `workflow_dispatch`
- Требует GitHub Personal Access Token (пользователь вводит один раз, хранится в localStorage)
- Показывает статус запущенного workflow

**Страница результата:**
- Блоки сгруппированы по категориям (B2C / B2B / GEO)
- Для каждого: статус, контент, источники
- Кнопка "Скачать черновик" (markdown файл)
- Кнопка "Копировать TZ" (полный текст для копирайтера)

## Аналог: sf_pipeline (справка)

sf_pipeline — аналогичная система для бизнес-историй. Из неё берутся паттерны:

- **Per-topic passes** с ординальными словами (ВТОРОЙ, ТРЕТИЙ, ... ДВАДЦАТЫЙ ПРОХОД)
- **Self-prompting**: `«Знаю ли я ещё одну историю по этой теме?»`
- **id_topic_map**: маппинг ID записи → топик прохода
- **Serper + Tavily + Flash Lite**: цепочка верификации через веб
- **CARQ формат**: ID / C / A / I / Q — аналог будет BLOCK / CONTENT / CONFIDENCE / VERIFY
- **Emit + SSE**: потоковая передача событий в браузер

### Ключевые технические решения sf_pipeline:

1. **Один промпт на всю область** (не отдельные запросы на каждый топик) — дешевле и быстрее
2. **Ординальные слова вместо === ПРОХОД N ===** — модель надёжнее генерирует все проходы
3. **knowledge_items** — список `{area, text, id_topics}`, а не строка — позволяет трекать топики
4. **max_tokens=1200** для факт-карточек (600 было мало, текст обрезался)
5. **"Отвечай сразу без преамбулы"** в промпте факт-карточки — модель иначе тратит токены на вступление

## Открытые вопросы (решить в новом чате)

1. **Один промпт или раздельные?** Собирать все блоки в одном большом промпте (как sf_pipeline) или делать отдельный вызов на каждый блок-группу?
   - *Один промпт — дешевле и сохраняет контекст между блоками*
   - *Раздельные — проще отлаживать и переспрашивать*

2. **Маркетинговый комплекс**: если анализов несколько (ТТГ + Т4св + АТ-ТПО), делать один общий документ или три отдельных + раздел сравнения?

3. **Конкурентный анализ**: нужно ли автоматически скрейпить страницы конкурентов (Хеликс, Mayo Clinic) для конкретного анализа и включать в верификацию?

4. **Медицинский ревьюер**: блок 16 (Автор/Рецензент) — нужен ли шаблон для заполнения вручную после генерации?

5. **Версионирование**: при повторном запуске для того же анализа — перезаписывать или хранить историю версий?
